# LIVE STUDIO ASR — Contrato de autenticação V1.1

## Objetivo

A V1.1 separa a autenticação da interface e permite trocar o login local por um backend seguro sem alterar as telas que consomem `AuthService`.

## Modo de desenvolvimento

Quando `ASR_AUTH_API_BASE_URL` não estiver definido, o aplicativo usa o provedor local da V1 para desenvolvimento/homologação.

## Modo de produção

Configure:

```bash
flutter build web --release --dart-define=ASR_AUTH_API_BASE_URL=https://api.seudominio.com
```

O mesmo parâmetro pode ser usado nos builds Android.

## Contrato REST

### Login

`POST /v1/auth/login`

Request:

```json
{
  "email": "usuario@dominio.com",
  "password": "senha-do-usuario"
}
```

Resposta de sucesso (2xx):

```json
{
  "user": {
    "email": "usuario@dominio.com"
  }
}
```

### Sessão atual

`GET /v1/auth/me`

Resposta de sucesso (2xx):

```json
{
  "user": {
    "email": "usuario@dominio.com"
  }
}
```

### Logout

`POST /v1/auth/logout`

Qualquer resposta 2xx significa sucesso.

## Segurança

O cliente não persiste senha nem token de longa duração. O backend deve usar sessão segura, preferencialmente cookie `HttpOnly`, `Secure` e `SameSite` adequado ao domínio, ou outro mecanismo equivalente com rotação/expiração.

O backend também deve implementar rate limiting, política de senha, expiração de sessão, encerramento de sessão e autorização por usuário.

## Critério para remover o fallback local

Depois que o backend real estiver homologado, os builds de produção devem sempre definir `ASR_AUTH_API_BASE_URL`. O provedor local deve permanecer apenas para desenvolvimento/testes até a estratégia de produção ser concluída.
